# PortMaster / R36S build

The PortMaster build is an additional Godot `Linux/X11` PCK export named `PortMaster (Godot 4.7)`. Its `portmaster` custom feature isolates handheld startup, 4:3 UI scaling, and fixed-screen settings from the Android, desktop Linux, and Windows exports.

## PortMaster-only package trimming

The PortMaster export excludes two confirmed non-game assets: `assets/itch_cover_supermarket_the_night.png` is not referenced by project source, and `assets/generated/rooms/market_clean_shift_start_passage_candidate.png` is a draft image whose filename cannot be produced by the runtime room-state loader. That loader only builds `<art_prefix>_<state>.png` for the four room states selected in `levels/arena/arena.gd`. The exclusions are scoped to the PortMaster preset; desktop and Android resource filters are unchanged. The Godot 4.7.1 package rebuild completed with both paths absent from the PCK. The latest PCK is 86,295,328 bytes, down 3,414,576 bytes (about 3.3 MiB) from the previous 89,709,904-byte build; the ZIP is 86,811,438 bytes (about 82.8 MiB). ZIP integrity passed. This reduces download/storage size only; it is not an ARM memory or frame-time optimization.

## Handheld screen layout

Classic R36S variants listed by dArkOSRE use a 640×480 4:3 panel. The same device database also lists square 720×720 variants, including R36S Plus and some clones, so the port must use PortMaster's detected `DISPLAY_WIDTH` and `DISPLAY_HEIGHT` instead of assuming every R36-family device is 640×480. At startup the game sets Godot's `content_scale_size` to 1.5 times the detected panel dimensions and uses `CANVAS_ITEMS` with `EXPAND`. On a 640×480 panel this makes a 960×720 logical canvas, giving interface text and panels more physical pixels than the desktop 1920×1080 design canvas while preserving the display aspect. The PortMaster title panel gets extra width for long Turkish labels, and the title character shifts right to keep the menu clear. Controller UI sizes do not use phone DPI-derived touch sizing. The camera fits the full store width on 4:3. The PortMaster receipt has a D-pad-focusable `MORE` / `DİĞER` action that opens manual, records, and credits; the header hamburger remains an optional pointer shortcut. All these changes are behind the `portmaster` feature; the Android, desktop Linux, and Windows project scale and camera paths remain unchanged.

Host smoke coverage: a temporary Godot 4.7.1 x86_64 export with the `portmaster` feature was rendered through gamescope's headless compositor at 640×480, 720×720, and 1280×720. Title, character, and difficulty screens were visually checked at all three sizes. The title receipt was widened, PortMaster-only menu labels were shortened, and character selection was compacted so its title and action buttons fit within the small panel. A 320×240 capture clipped the title and character UI; the package's `!lowres` requirement excludes those devices. A virtual Xbox 360 controller is recognized by SDL, and gptokeyb2 translates its A/D-pad events into Linux uinput Enter/arrow key events. However, this host's nested gamescope headless backend does not forward that uinput keyboard to its child window, while direct X11 keyboard injection does. That makes this host gamepad test inconclusive for the actual Westonpack path; it is not evidence that R36S input works. Physical controller behavior, ARM64 performance, audio, firmware compatibility, and suspend/resume still require the handheld before calling the port device-tested. The PortMaster-New contribution guide calls for a firmware/device test matrix; do not treat one x86_64 simulation as that validation.

## Diagnosis from the supplied dArkOSRE log

The attached device log identifies dArkOSRE `03082026`, PortMaster `2026.06.23-0015`, an aarch64 Cortex-A35 with 1 GB RAM, and a 640×480 panel. It contains two concrete launch failures:

- PortMaster `get_controls` fails reading `/tmp/gamecontrollerdb.txt` with `Permission denied`. The failing read occurs after a prior privileged run left the shared temporary file owned or protected such that the game launcher could not load it. The launcher now removes that file through `ESUDO` before rebuilding the SDL mapping and stops with an actionable message if PortMaster still returns an empty map.
- Godot could not open the PCK because the launcher looked one directory too deep inside the installed port data directory. The launcher now checks `/ports/supermarketthenight/SupermarketTheNight.pck`, matching the actual ZIP layout, and keeps a script-relative fallback for frontends that launch a copied entry. A missing PCK now produces a clear reinstall message instead of an empty/grey game window.

The same log shows Weston discovering and configuring `Fake Keyboard Mouse` through libinput. That proves the gptokeyb virtual keyboard device reached Weston in this run; it does not prove gameplay because Godot exited when the PCK could not be opened. The Weston `integer expression expected` warning is followed by successful headless, kiosk, Crusty EGL, Xwayland, and seat setup, so it was not the observed immediate exit cause. The next decisive check is installing this rebuilt archive on the R36S, confirming the controller-map permission error is gone and the PCK opens, then testing each mapped control in-game.

## Device and runtime requirements

- 64-bit ARM (`aarch64`) handheld running a PortMaster-compatible firmware. This includes current R36S ArkOS-family builds when their PortMaster runtime supports the device.
- PortMaster's Godot 4.7.1 and Westonpack 0.2 shared runtimes.
- Compatibility renderer, ETC2 texture export, keyboard-emulated controller input through `gptokeyb2`.
- PortMaster input is isolated by the `portmaster` custom feature: left stick sends WASD to gameplay movement, D-pad arrows navigate focused menus, and Godot's UI joypad mappings are removed to avoid duplicate navigation. A sends Enter to activate the focused control; B sends Escape to cancel/go back; X sends E for interaction; Y sends R to restart after a run; Start sends Escape to pause/resume; L1/R1 send left/right mouse clicks while the right stick moves the pointer. The launcher uses the `GPTOKEYB2` helper with the port's `.ini` profile. It sets `CRUSTY_BLOCK_INPUT=1` to block Crusty's parallel native controller path. Existing desktop and Android input paths remain in place.
- `control.txt:get_controls` builds `/tmp/gamecontrollerdb.txt`; the launcher removes an unwritable stale file before calling it. This recovers from a prior root-owned file that otherwise prevents PortMaster from loading the device's SDL mapping.
- Internet access the first time the two shared runtimes are installed.

PortMaster-New's `runtimes/runtimes.json` currently lists `godot_4.7.1.squashfs` and `weston_pkg_0.2.squashfs`. The Godot runtime contains `godot471.aarch64`; the Westonpack runtime contains `westonwrap.sh` and its `crusty_x11egl` renderer. The launcher uses those published filenames, and its `attr.runtime` names must match the manifest entries exactly.

The game targets Godot 4.7 and the runtime registry currently exposes Godot 4.7.1. The R36S hardware and each firmware build still need a device-level launch, input, audio, suspend/resume, and performance check before claiming release compatibility.

## Controller mapping references

The mapping uses PortMaster's logical controller names, not raw button IDs: D-pad arrows drive Godot focus, left analog directions map to WASD, and right analog directions move the mouse. dArkOSRE's `es_input.cfg` maps each supported board's physical buttons/axes to logical `a`, `b`, `up`, `down`, `left`, `right`, and analog controls. PortMaster uses that device mapping to build the SDL controller config passed to gptokeyb2. dArkOSRE also supports changing control schemes and button swaps, so this port relies on the logical SDL names and does not hard-code one R36S GUID or physical button number. The legacy ArkOS-R3XS repository points R36S users to dArkOSRE.

The PortMaster-New Godot launchers and controller profiles for Cave Crawler, A Key(s) Path, A Meta Data Game, Crop and Claw 2, and Forsworn were inspected. Their `.gptk` files use the same legacy logical-button syntax, but keyboard actions differ by game; this confirms the profile must reflect this game's focus, movement, interaction, and pause semantics rather than copy another game's button assignments. The Crop and Claw 2 and Forsworn Godot launchers use the same Westonpack `headless noop kiosk crusty_x11egl` chain, detected display size, `CRUSTY_BLOCK_INPUT=1`, and `.gptk` handoff; Forsworn additionally clears `LD_PRELOAD` for Godot because Crusty can interfere with EGL loading. Crop and Claw 2 uses Godot 4.6.3 while Forsworn uses 4.5; this port remains pinned to the installed PortMaster Godot 4.7.1 runtime. The supplied dArkOSRE log confirms Weston sees gptokeyb's virtual keyboard, while the separate PCK error stopped Godot before gameplay. `CRUSTY_BLOCK_INPUT=1` follows the official Weston/Godot chain.

### Broader upstream Godot-port scan

The full `PortsMaster/PortMaster-New` main-branch tree was scanned for Godot-runtime `port.json` entries, launchers, and bundled `.gptk` profiles, rather than relying only on the six-port examples checkout. The current upstream tree has 39 ports declaring a shared Godot runtime. Every one of their launchers uses Westonpack; 36 invoke the `GPTOKEYB` wrapper and 3 invoke `GPTOKEYB2`. Their shared Godot runtimes span Godot 4.2 through 4.6.3 (14 ports use 4.3, 9 use 4.2.2, 6 use 4.5, 6 use 4.4/4.4.1, 2 use 4.6.3, and 2 use 4.2/4.3.0). The current Godot 4.7.1 runtime is listed in PortMaster-New's `runtimes/runtimes.json`, so this project can use that shared runtime without bundling an engine binary. PortMaster-New's contributor rules require every `attr.runtime` value to match that manifest exactly.

Of the 36 Godot-port `.gptk` files directly present in those ports, 25 map the D-pad to arrow keys, 22 map the left stick to arrows, 6 map it to WASD, and 7 use mouse input; three ports generate or select their controls dynamically. These values overlap because profiles can implement more than one behavior. The common pattern is keyboard emulation, but the exact buttons vary per game. This port intentionally uses arrows for focus navigation, WASD for continuous player movement, right-stick mouse movement, and face buttons mapped to its own action semantics. It gates those input actions behind the `portmaster` feature so desktop and Android input remain unchanged.

### Full upstream controller-profile scan

The refreshed `PortMaster-New` sparse checkout contains all 1,058 current `.gptk` profiles, not just the Godot subset. I parsed each profile's active `button = mapping` entries, ignoring comments. In this all-port sample, 583 profiles map all four D-pad directions to arrow keys, 114 map at least one left-stick direction to WASD, 276 use mouse mappings, and 99 map the right stick to mouse movement. Counts overlap and describe profiles, not unique games; several ports ship multiple profiles. The R36S control design follows common handheld conventions while supporting this game's actual interaction model: focused menus get digital D-pad keys, movement gets analog WASD, and pointer controls remain available for panels that use the mouse.

The face-button scan also confirms there is no universal A/B/X/Y mapping across ports: A and B are variously mapped to Enter, Space, mouse clicks, or game-specific keys. The current port uses the logical A button for Enter and B for Escape, matching its focus-based menu actions. X remains `E` for in-world interaction, Y is `R` for restart, and Start is Escape for pause. This is chosen from this game's input actions, not copied blindly from a neighboring port.

The upstream helper variables are command strings rather than executable paths. `control.txt` currently defines `GPTOKEYB` as the classic helper plus the firmware-specific kill option, and `GPTOKEYB2` as the newer helper wrapped with its interpose library and `-Z`. dArkOSRE's own PICO-8 launcher uses `/opt/inttools/gptokeyb -1 <application> -c <profile>`; PortMaster's general launcher contract exports helper commands and ports call them as `$GPTOKEYB2 <application> -c <profile>` or `$GPTOKEYB <application> -c <profile>`. The project launcher prefers the newer helper, then falls back to the classic variable. The two helper repositories document legacy `button = key` mappings and analog deadzone controls; gptokeyb2 also supports its newer sectioned format. Keeping this port's profile in the shared legacy syntax makes the same mapping readable by either helper. PortMaster-New's contributor rules say to finish launch scripts with `pm_finish` and avoid custom `trap`/`pkill` cleanup; this launcher leaves helper shutdown to `pm_finish` after the Weston and runtime cleanup.

The controller configuration failure from the supplied log matches the current PortMaster `control.txt` implementation: `get_controls` writes `/tmp/gamecontrollerdb.txt` with an unprivileged shell redirection, so it cannot overwrite a stale root-owned file. The launcher deletes the stale file using the firmware's `$ESUDO` before calling `get_controls`, then checks that PortMaster returned a nonempty mapping. It also loads the `.gptk` from the data directory (`$GAMEDIR/supermarketthenight.gptk`); a previous extra directory component made the mapper miss the profile and silently use its defaults. This recovery does not hard-code any R36S controller GUID or key numbers.

Additional integrated-game reference: [Verdant Crown](https://github.com/avidela/verdant-crown) has an R36S-specific Weston/Godot launcher and a frame-time instrumentation guide. Its useful practice is to report per-zone p50/p95/p99/max frame-time distributions and separately track transition hitches, rather than infer handheld performance from desktop average FPS. This project still needs actual R36S telemetry before setting an ARM performance claim.

## Build a package

Install Godot 4.7.1 and set `GODOT_BIN` if the executable is not on `PATH`:

```sh
GODOT_BIN=/path/to/godot-4.7.1 ./scripts/build_portmaster.sh
```

The script imports project assets, exports the PCK into `port/supermarketthenight/supermarketthenight/`, and creates `builds/portmaster/supermarketthenight.zip`. The archive root contains the launcher and one `supermarketthenight/` folder. That folder contains `port.json`, `supermarketthenight.md`, `gameinfo.xml`, the 640×480 screenshot, the PCK, gptokeyb2 `.ini`, and licenses. `testing_thread.txt` is kept separately as a post for the PortMaster testing channel, not installed as game content. It does not export or rewrite the Android, desktop Linux, or Windows presets.

PortMaster catalog metadata is kept alongside the package in `port/supermarketthenight/`: `port.json`, `README.md`, the launcher, `gameinfo.xml`, `testing_thread.txt`, 4:3 gameplay screenshot, controller mapping inside the port directory, and license notices. The Godot and Westonpack runtimes are installed by PortMaster and are not copied into the game archive. The `attr.runtime` values use the exact current catalog keys, including their `.squashfs` suffix.

The launcher is tracked with mode `0644` per current PortMaster-New reviewer guidance. The ZIP follows the downloaded Brotato and other PortMaster examples: a root launcher plus one port folder containing metadata and game files. The `port.json` `items` array lists only those two install entries.

## PortMaster-New submission steps

The game repository package is a candidate package, not an official catalog submission. Before opening a PortMaster-New PR, follow the current upstream contribution instructions: test the release package with the PortMaster community in Discord `#testing-n-dev`, fix reported issues, and document a hardware/firmware matrix across Rocknix, MuOS, dArkOS, Knulli, and ArkOS (AmberELEC is optional). Upstream also advises varying resolutions: 640×480, 1024×768, 1280×720, optional 720×720, and 320×240. Then add only this port under `ports/supermarketthenight/` in a PortMaster-New fork, run `python3 tools/build_release.py --do-check`, and submit a PR. Host-side checks do not satisfy the community hardware test stage.

## Controls

The PortMaster controller profile maps left stick to WASD gameplay actions, D-pad to non-repeating arrow keys for menu focus, right stick to mouse movement, A to Enter (focused UI confirmation), B to Escape (back/cancel), X to E (nearby console interaction), Y to R (restart from results), Start to Escape (pause), and L1/R1 to left/right mouse clicks. The PortMaster title removes native gamepad events from Godot's UI actions and consumes raw SDL gamepad events before focused controls see them, so the gptokeyb keyboard event is the sole menu input. WASD and arrow keys are separate in the PortMaster player movement path. The standard desktop, Linux, Windows, Android, and touch input paths remain unchanged.

The package layout follows the downloaded PortMaster examples: the launcher is at the ZIP root, while catalog metadata and game files are inside the port folder. The `gameinfo.xml` uses EmulationStation's `desc`, `releasedate`, `developer`, `publisher`, `genre`, and `image` fields. On install, HarbourMaster imports these fields into the ports `gamelist.xml` when its **Metadata Update: Auto** setting is enabled (the default). If metadata remains missing after reinstall, check that setting and use PortMaster's **Update gamelist.xml** action; deleting the EmulationStation list alone does not trigger a PortMaster import.

The R36S shop now has its own compact 4:3 layout with all three offers, the full stat ledger, inventory summary, six weapon slots, and return action in view. PortMaster skill/level-up choice cards omit item pictures to give effects and descriptions more room, expose the whole card as the A/Enter focus target, and use a thicker blue focus frame. These are PortMaster-only branches; Android and desktop UI paths are not changed. No Android device is used for this work, and actual R36S button/firmware behavior still needs the handheld for confirmation.

Passing `godot471` (<15 chars) ensures clean termination without locking up controls.
- **Shop UI Focus & Visuals**: Weapon visuals now use proper ordering and fallback loading; focus outline frames were added for category buttons, inventory, and weapon slots; skill choices are enlarged and balanced for 480p landscape without bottom clipping.

  - Difficulty select: Fixed navigation cycling bugs; resized tier buttons to 72×44 so all 6 difficulty levels fit on a 640×480 screen without horizontal overflow; styled locked start button cleanly without overflowing focus boxes; shortened modifier text.
